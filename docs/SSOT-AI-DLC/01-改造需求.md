## 2. SSOT 定位(对齐 realignment)

SSOT 是**面向软件开发生命周期的项目文档统一管理平台**,统一管理所有项目文档(过程资料 + 正式文档正文 + 逆向文档),提供版本管理、向量化检索、MCP 服务与 Web Portal。

对 AI-DLC 而言,SSOT 是**文档来源与文档去处**,不是需求/决策的审批控制平面:
- **读**:通过 MCP 检索/读取项目已有文档,作为编写蓝图/PRD 等正式文档的上下文;
- **写**:通过 MCP 把 AI-DLC 产出的正式文档(蓝图/PRD/架构/设计/测试)与存量项目逆向文档写回 SSOT;
- SSOT **不**托管 AI-DLC 的需求审批状态、CR 流程或工作单元锁——这些仍由本仓 `docs/aidlc/state.md` 与 Git 产物本地权威管理。

## 3. 当前 AI-DLC 基线(保留的核心约束)

- 三阶段生命周期:Inception、Construction、条件化 Operations;
- `docs/aidlc/state.md` 是跨 Kiro、Claude Code、OpenCode 恢复的唯一状态源(**保持 state 模式版本 2**);
- 每步完成必须更新 `state.md`、审计、验证更新并输出摘要;
- 需求语义或契约变化必须走 CR1—CR5(**在本仓本地进行**);
- 审批模式按 `core-workflow.md`:标准为默认,团队协作或高风险才升严格;SSOT 侧为**轻量变更记录**;
- 代码、机器契约、配置和真实执行证据由工作区及外部平台提供;
- 不允许 AI 推翻已确认的决定;
- 未执行、仅口头或缺少稳定标识的检查必须标记为未验证。

引入 SSOT 只是为 AI-DLC 增加一个**文档检索与正式文档沉淀的外部平台**,不把 AI-DLC 变成远程工作流引擎,也不把需求审批权移交 SSOT。

## 4. 改造目标

1. AI-DLC 可配置 SSOT 连接(base URL + API Key)并绑定**一个项目**(SSOT 的 project);
2. 不同工具入口(Kiro/Claude/OpenCode)读取同一 SSOT 项目的同一批文档;
3. AI-DLC 在需要时通过 MCP **按需检索** SSOT 文档片段作为上下文,而非全量加载;
4. AI-DLC 在 Inception 产出蓝图/PRD/架构/设计/测试等正式文档后,可经 MCP 写回 SSOT(type=formal);
5. 对存量项目,AI-DLC 可经 MCP 写入逆向工程文档(type=reverse,关联 Git commit/哈希);
6. SSOT 不可用时,AI-DLC 仍可从 `state.md` 恢复并继续本地流程(检索/写回降级为跳过并记录待补);
7. 支持多项目:单次 AI-DLC 会话只绑定一个 SSOT 项目;
8. 未配置 SSOT 的项目继续使用现有 AI-DLC 流程,不受影响。

## 5. 非目标

- 不用 SSOT 取代 `state.md`、Git、任务系统、CI 或部署平台;
- 不把 AI-DLC 的需求审批/CR 权威移交 SSOT(SSOT 只存文档正文与版本);
- 不引入 org/项目群/发布/基线的多级绑定层级(SSOT 只有扁平 project);
- 不引入 state v3、ssot-manifest、事件游标、关系图版本等控制平面机制;
- 不做双仓 Provider/Consumer 契约版本治理、成对前滚/回滚;
- 不让 Agent 自动批准需求、架构、安全和发布决定;
- 不要求已有项目一次性迁移。

## 6. 权威来源边界(对齐后)

| 信息 | 权威来源 | AI-DLC 职责 |
|---|---|---|
| 项目文档(过程/正式/逆向)正文与版本 | SSOT(启用后) | 检索、读取、写入正式/逆向文档 |
| AI-DLC 阶段、步骤、模块、单元、活跃 CR | `state.md` | 唯一恢复与本地执行控制(本地权威) |
| 需求/故事/设计等 AI-DLC 派生产物 | Git 中的 AI-DLC 产物 | 生成、审查、版本关联;择要写回 SSOT 作为正式文档 |
| 代码和机器契约 | Git | 实现、审查、验证 |
| 单元认领 | Git/任务系统 | 展示,不重新发明锁 |
| CI、测试、制品、部署结果 | 外部平台 | 执行或记录稳定证据 |

## 7. 功能需求

### 7.1 连接与项目绑定

| 编号 | 需求 |
|---|---|
| ADLC-BOOT-001 | I1 检测 SSOT 连接配置(base URL + API Key 是否就绪)与 `state.md` 中的项目绑定。 |
| ADLC-BOOT-002 | 已绑定项目须能用 API Key 经 MCP 解析出该 project 及当前用户在其中的角色。 |
| ADLC-BOOT-003 | 无法唯一确定 SSOT 项目时必须询问,不得按仓库名猜测。 |
| ADLC-BOOT-004 | 一次只激活一个 SSOT 项目绑定;切换项目等同恢复流程。 |
| ADLC-BOOT-005 | 未配置 SSOT 时按未接入处理,原流程不受影响。 |

### 7.2 state.md(保持 v2)

| 编号 | 需求 |
|---|---|
| ADLC-STATE-001 | **保持状态模式版本 2**,不升级 v3。 |
| ADLC-STATE-002 | 新增可选字段:SSOT 是否启用、base URL 引用(不含密钥)、绑定的 project、最近检索/写回时间。 |
| ADLC-STATE-003 | `state.md` 只记录绑定与索引,不复制 SSOT 文档正文。 |
| ADLC-STATE-004 | API Key 不写入 `state.md`、审计或提示词,经环境变量/安全凭据存储提供。 |

### 7.3 会话恢复

| 编号 | 需求 |
|---|---|
| ADLC-SES-001 | 恢复先读 `state.md`,不先依赖 SSOT。 |
| ADLC-SES-002 | SSOT 不可用时正常本地恢复,检索/写回能力标记为暂不可用。 |
| ADLC-SES-003 | Kiro、Claude Code、OpenCode 恢复结果必须一致。 |
| ADLC-SES-004 | 不得用聊天摘要代替 state。 |

### 7.4 文档检索(读)

| 编号 | 需求 |
|---|---|
| ADLC-CTX-001 | 通过 MCP `search_documents` 按查询+可选 type 检索 SSOT 文档,返回 Top-K 片段与来源。 |
| ADLC-CTX-002 | 需要完整正文时用 `get_document`(默认当前版本,可指定历史版本)。 |
| ADLC-CTX-003 | 检索结果标注来源(document_id/version/片段),供在正式文档中引用溯源。 |
| ADLC-CTX-004 | 不得一次性加载项目全部文档;按当前步骤需要检索。 |
| ADLC-CTX-005 | 检索失败或 SSOT 不可用时不得以模型记忆冒充 SSOT 文档事实,须标记未取到。 |

### 7.5 正式文档写回(写)

| 编号 | 需求 |
|---|---|
| ADLC-W-001 | AI-DLC 产出的蓝图/PRD/架构/设计/测试文档,经用户确认后用 MCP `write_formal_document` 写回 SSOT(type=formal)。 |
| ADLC-W-002 | 写回采用完整正文(文本),由 SSOT 统一做版本管理与向量化;内容更新=写新版本。 |
| ADLC-W-003 | 对存量项目,用 `write_reverse_engineering` 写入逆向文档(type=reverse),关联 Git 仓库/commit/哈希。 |
| ADLC-W-004 | 写回流程由 AI-DLC 本地控制(本地编写 → 用户确认 → 写入 SSOT);SSOT 不负责审阅。 |
| ADLC-W-005 | 写回失败不阻断本地产物生成,记录"待写回 SSOT"并可重试。 |

### 7.6 CR 集成(本地为主)

| 编号 | 需求 |
|---|---|
| ADLC-CR-001 | AI-DLC 的 CR1—CR5 仍在本仓本地进行,不依赖 SSOT 审批。 |
| ADLC-CR-002 | 若变更涉及已写回 SSOT 的正式文档,CR4 完成后可把更新后的正式文档作为新版本写回 SSOT。 |

### 7.7 降级与错误处理

| 编号 | 需求 |
|---|---|
| ADLC-ERR-001 | SSOT 不可用时从 `state.md` 正常恢复本地位置。 |
| ADLC-ERR-002 | MCP 超时使用有限重试;写回使用幂等语义((document_id, 内容 sha256) 由 SSOT 保证不重复)。 |
| ADLC-ERR-003 | 鉴权失败(缺失/无效 API Key、无项目权限)明确报告,不重试绕过。 |

## 8. MCP 依赖(以 SSOT `mcp-contract.md` 为准,共 14 工具)

AI-DLC 依赖 SSOT 提供的现行 MCP 工具(凭据经 `Authorization: Bearer` 头,不作为工具入参):

```text
list_projects / get_project
create_document / upload_revision
list_documents / get_document
activate_revision / archive_document / restore_document
search_documents / retrieve_context
write_formal_document / write_reverse_engineering
get_revision_file
```

AI-DLC 主要使用:`search_documents`/`retrieve_context`/`get_document`(读上下文)、`write_formal_document`/`write_reverse_engineering`(写回)、`get_revision_file`(取图片/表格原文理解)。不存在旧设计中的 `project.resolve`/`baseline.verify`/`change.propose`/`checkpoint.publish` 等控制平面工具。

## 9. 验收标准

1. 未配置 SSOT 的项目行为与改造前一致;
2. 配置 SSOT 后,三平台绑定同一 project 并能检索到同一批文档;
3. `state.md` 保持 v2,不因接入 SSOT 而显著膨胀,且不含 API Key;
4. AI-DLC 能经 `search_documents`/`get_document` 取到文档片段并在正式文档中标注来源;
5. Inception 产出的正式文档能经 `write_formal_document` 写回 SSOT 并被后续检索到;
6. 存量项目逆向文档能经 `write_reverse_engineering` 写回并关联 Git 信息;
7. SSOT 不可用时本地恢复成功,检索/写回标记为暂不可用而非伪造结果;
8. 鉴权失败明确报告且不绕过;
9. 需求语义变化仍走本地 CR1—CR5,不被 SSOT 旁路;
10. 三平台语义一致。
