# Inception 产物交叉验证（强制审查）

**目的**：确保 Inception 阶段各产物之间保持一致性，问题发现越早成本越低。

**执行时机**：每个产物完成后立即执行对应的审查项，不等待所有产物完成。

---

## 审查项总览

| 审查项 | 执行时机 | 条件 | 步骤编号 |
|--------|---------|------|----------|
| a) 需求 ↔ 逆向工程 | 需求分析完成后 | 有逆向工程产物 | 3.1 |
| b) 需求 ↔ 澄清记录 | 需求分析完成后 | 始终 | 3.1 |
| c) 用户故事 ↔ 需求 | 用户故事完成后 | 始终 | 4.1 |
| d) 需求完整性评估 | 用户故事完成后 | 始终 | 4.1 |
| e) UI 设计 ↔ 用户故事+需求 | UI 设计完成后 | 执行了 UI 设计 | 5.1 |
| f) 页面基准产出物一致性 | 变更请求完成后（CR4 就地基线更新后） | 变更涉及已有页面 | CR5 |
| g) PRD ↔ I5-I10 产物一致性 | PRD 汇编完成后 | 执行了 PRD 汇编 | I16 |

**审查清单**：

| # | 检查点 | 通过标准 |

**未通过处理**：

## 审查项 f：页面基准产出物一致性（变更后）

**执行条件**：变更请求涉及已有前端页面（CR4 就地基线更新完成后触发）

**目的**：验证变更回写后，每个受影响页面的需求、用户故事、UI 设计三者描述一致且完整，防止同一页面出现多版本需求。

**输入文件**：
- 受影响页面的 UI 设计（HTML Mock 模式：对应 mock-box；Figma 模式：对应 Frame）
- 需求文档中描述该页面的段落
- 涉及该页面的所有用户故事
- 该页面的实际代码实现（如已有）

**审查清单**：

| # | 检查点 | 通过标准 |
|---|--------|---------|
| 1 | UI 设计中该页面是否包含变更后的所有功能入口 | 无遗漏入口 |
| 2 | 需求文档中该页面的描述是否反映变更后的完整状态 | 描述完整且无矛盾 |
| 3 | 是否存在同一页面的多份矛盾描述（不同文件中） | 无矛盾描述 |
| 4 | 源模块/单元中被迁移的功能是否已标记为"不再维护" | 旧描述已标记迁移 |
| 5 | 变更新增的功能是否已合并到页面基准（而非仅存在于变更日志） | 已合并到基准 |
| 6 | 代码实现中的页面内容是否与 UI 设计 + 需求一致 | 代码与产出物对齐 |

**未通过处理**：
1. 列出不一致项（明确指出哪个产出物缺失了什么内容）
2. 回退到 CR4 的就地基线更新，补充回写缺失的内容
3. 重新执行审查项 f 直到通过

**规则参考**：详细的页面级单一真相源判定规则见 `common-page-source-of-truth.md`

## 审查项 g：PRD ↔ I5-I10 产物一致性（I16）

**执行条件**：I15 已生成 PRD 工作稿。

**目的**：以可复现证据证明 PRD 只是当前场景 I5-I10 业务产物的汇编视图，不含新增、遗漏、悬空或失效语义。I16 通过前 PRD 禁止对外发出，I11 保持阻断。

**输入文件**：
- 单模块 `docs/aidlc/inception/prd.md`，或多模块 `docs/aidlc/product/scenarios/<scenario-id>/prd.md`
- 当前场景 `scenario-manifest.md`
- manifest 当前场景切片索引关联的 `requirements.md`、`business-flows.md`
- 条件适用的 `data-model.md`
- `stories.md`、`personas.md`、`role-permission-matrix.md`
- 条件适用的 `{端}-page-specs.md`
- 条件存在的澄清问题文件

### 审查前门禁

依次执行，任一失败即阻断，不得进入 13 项内容审查：

1. 验证 manifest §8 每个来源定位键符合对应语义类型固定格式，在对应模块、语义类型和来源路径内唯一，并关联当前场景 §4 中真实存在的 FR。
2. 验证 §9 对每个索引区块关联的每条适用来源路径独立记录；适用来源均为 `current`；以来源文件原始 UTF-8 字节重新计算 SHA-256，结果与 `sha256:<64 位小写十六进制>` 记录一致。
3. 验证 §9 的 `stale` 与 `not-applicable` 行满足路径、修订标识、RFC 3339 同步时间、依据及状态转换规则；任何 `stale` 适用来源均阻断。
4. 验证 §4-§8 不为空切片、不引用已失效索引；每项输入判定为 `适用且存在 / 不适用并有依据 / 应存在但缺失`。合法不适用只记录依据，不创建空产物；应存在但缺失时阻断并返回对应步骤。

### 审查清单

每项必须给出具体位置或数量证据；数量型结论使用“分子/分母”，禁止仅给百分比或“看起来一致”。

| # | 检查点 | 通过标准 | 违规后果 |
|---|--------|----------|----------|
| 1 | 零新增语义：PRD 每条业务语义能否定位到来源产物具体条目 | 无来源标注条目数 = 0 | **硬阻断** |
| 2 | FR 正向覆盖：manifest §4 当前场景 FR 是否都在 PRD 体现 | 当前场景 FR 全部覆盖，或有显式“本次不含”及理由 | 阻断 |
| 3 | FR 反向可溯：PRD 引用的每个 FR ID 是否真实存在 | 无悬空 FR ID | **硬阻断** |
| 4 | 验收标准是否与 `stories.md` Gherkin 语义等价 | 逐条比对，无语义增删改 | 阻断 |
| 5 | 页面清单是否与 manifest §6 一致并能在 page-specs 定位 | 当前场景切片双向无差集；无 UI 时有依据 | 阻断 |
| 6 | PRD 流程图是否与 `business-flows.md` 同源而非重绘 | 节点与分支完全一致 | 阻断 |
| 7 | manifest §8 状态条目是否与适用的 `data-model.md` 一致 | 每条关联当前场景 FR；逐迁移比对；不适用时有依据 | 阻断 |
| 8 | manifest §8 字段条目是否与适用的 `data-model.md` 一致 | 每条关联当前场景 FR；逐字段比对；不适用时有依据 | 阻断 |
| 9 | manifest §8 权限条目是否与权限矩阵一致 | 每条关联当前场景 FR；无新增角色、无扩大操作或数据范围 | 阻断 |
| 10 | manifest §8 数值与枚举条目是否与来源一致 | 每条关联当前场景 FR，逐项取值完全一致 | 阻断 |
| 11 | 未关闭非阻断澄清项是否全部透传 | 无遗漏；存在未关闭阻断项时不得进入 I15 | 阻断 |
| 12 | 是否存在仅来自在途 PRD、未经 I5-I10 确认的内容 | 此类内容数量 = 0 | **硬阻断** |
| 13 | PRD 术语是否与产品词典及 `common-terminology.md` 一致 | 无同义异名、无异义同名 | 阻断 |

### 强制证据

```markdown
## 审查项 g 溯源矩阵

| PRD 位置 | 业务语义摘要 | 来源标注 | 来源存在 | 语义等价 | 结论 |
|----------|--------------|----------|----------|----------|------|
| §3.5 第 4 条 | 门店停业时关联商品自动下架 | M03-FR-007 | ✅ | ✅ | 通过 |
| §7.2 第 2 条 | 停业超 30 天清理实例 | 无 | ❌ | — | **阻断：新增语义** |
```

除溯源矩阵外，FR、US、页面、状态、字段、权限、数值、枚举和澄清项的覆盖检查必须报告“已匹配数/应匹配总数”及双向差集。

### 未通过处理与状态转换

1. 检查点 1、3、12 任一违规时立即阻断，PRD 状态置为 `draft`，禁止进入 `ready-for-review` 或对外发出。
2. 违规语义应当存在但权威来源缺失时，返回对应 I 步骤补充，重跑该步骤交叉验证，再重新执行 I15/I16。
3. 违规语义由 PRD 汇编臆造时直接从 PRD 删除，禁止反向补进 I5。
4. 其他检查点失败时，按权威来源修正汇编；若暴露来源自身缺陷，仍须返回来源步骤并重审。不得直接改 PRD 掩盖来源问题。
5. 全部通过后，将 PRD 从 `draft` 更新为 `consistency-checked`；随后才可进入 `ready-for-review`。同步更新 manifest §7、§9、state.md 和审计。

## 审查结果输出格式

每次审查完成后，输出以下格式的审查报告：

```markdown
## 🔍 交叉验证报告 — 审查项 {a/b/c/d/e/f/g}

**审查时间**：{ISO时间}
**审查对象**：{被审查的产物}

### 审查结果

| # | 检查点 | 结果 | 说明 |
|---|--------|------|------|
| 1 | {检查点描述} | ✅/❌ | {具体说明} |
| ... | ... | ... | ... |

### 总结
- **通过项**：{N} / {Total}
- **未通过项**：{列出未通过项及原因}
- **整体结论**：✅ 通过 / ❌ 未通过，需修正

### 修正建议（如未通过）
1. {具体修正建议}
2. ...
```

---

## 与步骤完成协议的关系

- 审查步骤本身也是一个步骤，完成后必须执行步骤完成协议（更新 state.md、微型摘要、审计记录）
- 审查步骤在 state.md 中记录为 `{步骤编号} 交叉验证 ✅/❌`
- 如果审查未通过并修正后重新通过，在审计中记录"首次未通过 → 修正后通过"

## 完成消息模板

审查通过后，展示完成消息：

```markdown
# 🔍 交叉验证通过 — 审查项 {a/b/c/d/e/f/g}

> **📋 审查结果**：所有检查点均通过，产物一致性验证完成。

> **🚀 Boss，下一步？**
>
> ✅ **确认并继续** - 进入 {下一步骤名}
> 📋 **新 Session 继续** - 复制 `state.md` 中的交接提示词到新对话继续

---

> **💡 下一步执行提示词**（可直接复制使用）：
> ```
> 继续执行 {下一步骤名}
> ```
```
