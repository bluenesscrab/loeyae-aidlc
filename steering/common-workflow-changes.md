# 工作流在途调整

## 职责边界

本文件仅处理**尚未完成的流程步骤**的执行调整。

**本文件管辖**：添加/跳过/重做未完成步骤、调整执行顺序、变更执行深度。

**不属于本文件**：已建立基线的产品功能变更走 `change-request-process.md`（CR1—CR5）；缺陷修复和无行为重构直接进入受影响 Construction 步骤。

---

## 调整类型

### 1. 添加已跳过的步骤

**场景**：用户想要添加一个原本被跳过的步骤。

**处理方式**：
1. 确认请求并检查前置依赖是否满足；
2. 在 `state.md` 中将步骤标记为"待执行"；
3. 按正常步骤流程执行；
4. 现有后续产物可能需要修订以整合新信息。

### 2. 跳过已计划的步骤

**场景**：用户想要跳过一个已计划但未执行的步骤。

**处理方式**：
1. 警告影响：解释将缺少什么以及潜在后果；
2. 获取用户明确确认；
3. 在 `state.md` 中将步骤标记为"已跳过"并记录原因；
4. 后续步骤可能需要手动干预。

### 3. 重做当前步骤

**场景**：用户对当前步骤的结果不满意，想要重做。

**处理方式**：
1. 了解具体关注点，提供"修改"与"完全重做"两个选项；
2. 选择修改时直接就地更新产物；
3. 选择重做时重置步骤状态，从头执行；
4. 更新 `state.md` 反映当前状态。

**注意**：不创建 `{artifact}.backup.{timestamp}` 副本。Git 历史保留旧版本。

### 4. 重做已完成的步骤

**场景**：用户想回退并重做一个已完成的步骤。

**处理方式**：
1. 评估所有依赖于该步骤的后续步骤的影响；
2. 向用户解释完整级联影响，获取明确确认；
3. 如确认，重置受影响步骤的状态；
4. 就地修改受影响产物，从该步骤重新执行；
5. 更新 `state.md`。

**注意**：不归档、不创建备份副本。Git 历史是恢复来源。

### 5. 添加/移除工作单元

**场景**：用户想要在单元生成后添加、移除或拆分工作单元。

**处理方式**：
1. 评估已完成设计/代码的影响范围；
2. 就地修改 `unit-of-work.md`、`unit-of-work-dependency.md`、`unit-of-work-story-map.md`；
3. 将受影响单元标记为需要重新设计或重新实现；
4. 按正常流程处理受影响的工作单元。

### 6. 更改架构决策

**场景**：用户想要改变架构方向（如单体 → 微服务）。

**处理方式**：
1. 评估当前进度；工作流越早影响越小；
2. 从最早受影响的步骤重新开始；
3. 就地修改受影响产物。

### 7. 暂停工作流

**场景**：用户需要暂停并稍后继续。

**处理方式**：
1. 尽可能完成当前步骤；
2. 更新 `state.md` 反映当前状态和下一步交接；
3. 恢复时读取 `state.md` 并从中断处继续。

---

## 通用原则

1. **始终确认**：未经用户明确确认，不进行破坏性调整。
2. **就地更新**：修改现有产物，不创建副本或增量文档。
3. **Git 即历史**：不创建时间戳备份文件；Git 历史保留所有旧版本。
4. **state.md 同步**：每次调整后立即更新 state.md。
5. **边界清晰**：已建立基线的产品功能变更走 CR，不在本文件范围内处理。
